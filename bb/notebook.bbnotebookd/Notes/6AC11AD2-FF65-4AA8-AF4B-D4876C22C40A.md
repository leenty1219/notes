
  CurrencySyncService 崩溃分析与修复方案

  1. 问题现象

  - 崩溃位置：MyMoney/Classes/Sync/Service/Sync/Currency/CurrencySyncService.m:120，currencySyncMoreThanOneDays: 方法内 [[DateUtil gregorian] components:fromDate:] 调用
  - 崩溃栈底：icu::Calendar::complete() ← __cficu_ucal_get ← _CFCalendarDecomposeAbsoluteTimeV ← -[__NSCFCalendar components:fromDate:]
  - 触发链路：SyncStrategyManager.m:167 syncAccountBook:username:inDataSuite: → SyncStrategyManager.m:696 startFetchQuotesForCurrencyCode: → CurrencySyncService.m:43 → :74 fetchingExchangeQuotesWithDefaultCurrencyCode: → :109 canSyncCurrencyByCode: → :120 崩溃
  - 崩溃线程队列：com.feidee.mymoney.syncContext.简单账本 (serial)——来自 SyncStrategyManager.m:94，每个账本一条独立串行队列
  - 复现条件：概率性。同步账本触发汇率获取时，恰好另一线程同时在用同一个 NSCalendar 实例（多账本并发同步、或主线程同时做日期计算时窗口更大）。无法稳定复现，只能靠消除共享根治。

  2. 根因

  MyMoneyAppBaseComponents/MyMoneyAppBaseComponents/Utils/DateUtil.m:29,98-104：

  static NSCalendar *gregorian = nil;

  + (NSCalendar *)gregorian {
      if (gregorian == nil) {
          gregorian = [[NSCalendar alloc] initWithCalendarIdentifier:NSCalendarIdentifierGregorian];
      }
      return gregorian;
  }

  返回的是进程级静态共享的 NSCalendar 单例，无任何线程隔离。 NSCalendar 底层包装 ICU Calendar，内部持有可变字段状态，complete() 会就地计算并回填字段标志位。同一实例被多线程同时调用 components:fromDate: 时，ICU 内部状态被并发读写 → 在 icu::Calendar::complete() 崩溃。这是共享
  NSCalendar 的典型崩溃签名，与入参（lastSyncDate）是否合法无关。

  并发来源：[DateUtil gregorian] 在 MyMoney/Classes 下有 29 处外部调用，加上 DateUtil 自身十几个内部方法（normalizeTimeIntervalFromDate: 等）都在用同一个实例，主线程和各账本同步队列随时可能同时进入。

  3. 影响范围

  - 直接崩溃点：CurrencySyncService.m:120/128（Sync 模块属主工程业务代码，MyMoney / MyMoneyPro 主 App；具体 target membership 未逐一核对）
  - 潜在风险面：其余 28 处 [DateUtil gregorian] 调用 + DateUtil 内部方法，任何两处跨线程同时执行都可能崩，本次只是落在汇率同步队列
  - DateUtil 属 MyMoneyAppBaseComponents（先确认后再改目录），被所有链接该组件的 target 使用（含 Widget / Watch），改动需全量回归

  4. 修复策略（建议分两阶段）

  阶段一：业务层最小修复（不动敏感目录，可直接做）

  在 currencySyncMoreThanOneDays: 内改用方法内独立创建的日历实例：

  // [DateUtil gregorian] 返回全局共享的 NSCalendar 单例，被多线程并发调用
  // components:fromDate: 时会在 ICU 内部 (icu::Calendar::complete) 崩溃，
  // 这里改用方法内独立创建的日历实例，避免与其他线程共享
  NSCalendar *calendar = [[NSCalendar alloc] initWithCalendarIdentifier:NSCalendarIdentifierGregorian];
  NSDateComponents *lastComponents = [calendar components:(NSCalendarUnitYear | ...) fromDate:lastSyncDate];
  NSDateComponents *currentComponents = [calendar components:(NSCalendarUnitYear | ...) fromDate:[NSDate date]];

  要点：
  - 必须用 alloc/initWithCalendarIdentifier:；不要用 +calendarWithIdentifier: 工厂方法（可能返回缓存共享实例，起不到隔离作用）
  - 语义等价：原单例从未设置 timeZone/locale，新建实例默认行为一致，纯崩溃修复、零行为变化
  - 该文件 DateUtil.h 的 import 可一并移除（修复后无其他引用）
  - 局限：只消除本调用点崩溃，其他 28 处隐患仍在（由阶段二根治）

  阶段二：DateUtil 根因修复（敏感目录，单独分支 + 团队评审）

  +gregorian 改为按线程缓存独立实例，API 完全兼容、无重复分配开销：

  + (NSCalendar *)gregorian {
      // NSCalendar 非线程安全，全局共享单例被多线程并发调用
      // components:fromDate: 时会在 ICU 内部崩溃，改为按线程缓存独立实例
      NSMutableDictionary *threadDict = [NSThread currentThread].threadDictionary;
      NSString *key = @"com.feidee.DateUtil.gregorian";
      NSCalendar *calendar = threadDict[key];
      if (calendar == nil) {
          calendar = [[NSCalendar alloc] initWithCalendarIdentifier:NSCalendarIdentifierGregorian];
          threadDict[key] = calendar;
      }
      return calendar;
  }

  为什么是线程级实例而不是其他方案：
  - 加锁不行：单例被 return 出去后，调用方在 DateUtil 外部直接对实例调方法，内部锁管不住外部调用
  - copy 不行：NSCalendar 是 copy-on-write 包装，copy 后底层 ICU Calendar 仍共享，读操作（components:fromDate:）不触发写时复制
  - 每次新建可以但没必要：线程级缓存既隔离又避免高频日期计算路径的分配开销

  附带说明（已确认本次不改）

  currencySyncMoreThanOneDays: 只比较 day 字段：跨月同日（如上次同步 7月10日、今天 8月10日）时 abs(day-day)=0，会误判“未超过一天”而跳过当天汇率请求，与注释“每种汇率请求次数为每天一次”意图不符。如日后修正，改为比较 era/year/month/day 完整日期或用
  isDate:inSameDayAsDate:，改动仍限定在该方法内。

  5. 验证步骤

  阶段一：
  1. 编译验证：MyMoney、MyMoneyPro 两个 scheme 均编译通过
  2. 人工回归核心路径：
    - 多币种账本触发同步（下拉/自动），汇率请求正常发起、不崩溃
    - 同一天内重复同步，确认每日一次节流仍生效（不重复请求）
    - 断网/弱网触发，确认汇率缓存兜底（cachedQuotesForCurrencyCode）正常
  3. 并发压测（可选，针对原崩溃场景）：≥2 个多币种账本同时触发同步 + 主线程频繁日期计算，制造并发窗口；修复后该点使用独立实例，理论不可能再崩
  4. 单元测试说明：该方法依赖 [NSUserDefaults standardUserDefaults] 且为私有方法，直接自动化需先做注入重构，超出最小改动范围，本次以人工回归为主

  阶段二（DateUtil）：
  1. 编译验证：所有链接 MyMoneyAppBaseComponents 的 target——MyMoney、MyMoneyPro、Widget、Watch/Extension 全部编译通过
  2. 并发单元测试（可落 MyMoneyAppBaseComponentsTests）：多线程并发调 [DateUtil gregorian] 做 components:fromDate: / dateFromComponents:，循环压测不崩溃
  3. 日期功能回归清单：
    - 记账页日期选择、账单列表按日分组
    - 报表日/周/月/年统计区间（normalizeTimeIntervalFromDate: 等）
    - 账本结转、封账日期
    - 周期记账/重复账单日期展开
    - 同步模块（本次崩溃链路）
  4. 性能抽检：报表页滚动等高频日期计算路径无明显劣化

  6. 风险与未验证项

  - 崩溃为概率性并发问题，无法稳定复现，验证以代码审查 + 并发单测/压测为主
  - 阶段一落地前（或仅落地阶段一），其余 [DateUtil gregorian] 调用点仍有低概率同类崩溃
  - DateUtil 改动影响所有 target，必须走团队评审， regression 范围大是本次拆成独立分支单独处理的原因
