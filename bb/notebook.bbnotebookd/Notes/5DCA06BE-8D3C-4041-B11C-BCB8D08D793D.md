当前理解

 SCTransactionBatchEditViewController 选中流水后直接 push SCTransactionShareViewController。问题更像是分享页预览长图一直停留在占位态，或长图内的网络图片缺失；两种现象在当前实现中有不同高概率原因。

 调用链

 ```text
SCTransactionBatchEditViewController.shareItemDidClick
  → selectedTransactionsWithSelectedDatas
  → SCTransactionShareViewController initWithAccountBookID:transactions:
  → viewDidLoad
  → reloadSettingConfigWithCompletion
  → loadBackgroundImageAndRender
  → SCTransactionShareImageRenderer renderImage...
  → displayRenderedImageWithAnimation
 ```

 关键文件：

 - MyMoney/Classes/SuiCloud/SCTransactionList/SCSuperTransaction/BatchEdit/SCTransactionBatchEditViewController.m:1040-1055
 - MyMoney/Classes/SuiCloud/SCTransactionList/SCSuperTransaction/Share/SCTransactionShareViewController.m:272-349
 - MyMoney/Classes/SuiCloud/SCTransactionList/SCSuperTransaction/Share/SCTransactionShareImageRenderer.m
 - MyMoney/Classes/SuiCloud/SCTransactionList/SCSuperTransaction/Share/view/SCTransactionShareComponentFactory.m

 当前分享模块无 PRO_VERSION / STANDARD_VERSION 分支；标准版和专业版共用这段实现。

 高概率原因

 ### 1. 背景图前置请求无超时/降级，任一回调不返回会永久不触发渲染

 loadBackgroundImageAndRender 并行等待：

 1. reloadImageWithPosition:accountBookID:completion:
 2. queryAccountBookTemplateWithCompletion:

 见 SCTransactionShareViewController.m:287-324。

 只有两个 completion 都执行了，dispatch_group_notify 才会调用 renderContentToImage。背景图本身是可选内容，但实现把它作为渲染的强前置条件；网络切换、请求取消、服务层未回调或极端网络异常时，页面会一直停留在 skeleton，占位图不会被替换。

 这最符合“偶现整张分享图片不展示”。

 ### 2. 网络图片加载依赖固定延迟，不保证图片实际完成

 长图中的三类图片都异步加载：

 - 分享背景：sd_setImageWithURL:
   SCTransactionShareComponentFactory.m:34-39
 - 用户头像：sd_setImageWithURL:
   SCTransactionShareComponentFactory.m:83-87
 - 流水附件：SCTransactionCell 内的 fd_setImageWithURL:...FDWebImageLowPriority | FDWebImageRetryFailed
   SCTransactionCell.m:601-624

 渲染器没有等待这些下载完成，只按附件数量固定等待：

 - 少于 10 张附件：0.5s
 - 10–39 张：2s
 - 40 张及以上：3s

 见 SCTransactionShareImageRenderer.m:1008-1025。

 固定时长无法覆盖弱网、首次下载、CDN 慢响应、SDWebImage/FDWebImage 低优先级排队、缓存未命中等情况。因此：

 - 预览长图本身可出现；
 - 但背景、头像、流水附件可能是默认图、空白或尚未绘制。

 这是“分享长图已展示，但图内图片不展示”的直接原因。

 ### 3. 分页渲染没有像单页路径一样限制实际像素尺寸，存在内存或位图尺寸失败风险

 单页路径会按 $15,000$ px 上限压低 renderScale：

 - SCTransactionShareImageRenderer.m:223-235

 但 20 条以上流水或超高分组进入分页路径后：

 - 每页最大逻辑高度可达 10,000 pt；
 - renderViewToImage: 仍使用 self.renderScale，最高可为 3.0；
 - 因而单页理论位图高度可达 30,000 px；
 - 多页后还会再次 combineImages: 合成长图。

 见：

 - 分页判断：SCTransactionShareImageRenderer.m:157-186
 - 分页渲染：544-743
 - 合图：937-994

 这会随流水备注长度、附件数量、设备内存状态而变化，符合“偶现”。失败结果可能是：

 - UIGraphicsImageRenderer 无法稳定产出完整位图；
 - 大图编码/合图瞬时内存过高；
 - 渲染结果为 nil，页面仅提示“准备分享数据失败”；
 - 低内存时生成结果不稳定或被系统终止。

 ### 4. 超大 section 二次拆分遗漏 processedData，会造成渲染数据不完整

 splitLargeComponent: 新建的 componentData 只保留：

 ```objc
dateHeader
transactions
isFirstBatch
sectionIndex
 ```

 未保留 processedData：

 - SCTransactionShareImageRenderer.m:704-709

 但 createSectionView: 会将 data[@"processedData"] 传给 SCTransactionShareComponentFactory：

 - SCTransactionShareImageRenderer.m:910-921

 随后 createSectionViewForSectionIndex: 访问 processedData.dateHeaders，并用它判断全局最后一条流水：

 - SCTransactionShareComponentFactory.m:254-256
 - SCTransactionShareComponentFactory.m:292-294

 该路径只在 section 高度超过 maxImageHeight 时命中，因此不是常规复现条件；但一旦某些流水因超长备注、图片区域或展示配置使 section 过高，可能引发异常或渲染中断。

 ### 5. 无渲染阶段可观测性，线上无法区分“前置请求卡住”“渲染失败”“图片未加载完”

 当前页面仅在最终 completion 中区分成功与失败：

 - SCTransactionShareViewController.m:339-348

 没有记录：

 - 偏好设置加载耗时；
 - 背景偏好、账本模板各自是否回调；
 - 最终背景来源；
 - 单页/分页策略；
 - 逻辑尺寸、实际像素尺寸、scale；
 - 渲染和合图耗时；
 - drawViewHierarchyInRect: 是否失败；
 - 图片 URL 下载是否在截图前完成。

 因此目前只能从实现推断，不能由线上证据定位到单一根因。

 建议修复顺序

 1. 先解除背景图请求对渲染的强依赖。
    对两个前置请求各自设置兜底完成；超时后立即使用本地默认背景执行渲染。背景图不可用不应阻塞分享能力。
 2. 将“固定等待”改为“实际图片加载完成或到达统一超时”。
    渲染前统计背景、头像、流水附件的有效 URL，以 dispatch_group 或现有图片加载回调汇合；超时后以占位图渲染，而不是无限等待或盲等 0.5–3 秒。
 3. 统一单页与分页的位图尺寸限制。
    每个分页组都按实际 width × height × scale 限制到 GPU/内存安全范围；合图前再次评估总像素，必要时降低 scale 或保留多页分享，不应无上限拼接高分辨率长图。
 4. 修复超大组件拆分的数据完整性。
    在 splitLargeComponent: 的 componentData 中保留 processedData；避免进入极端分页时取到 nil 数据。
 5. 补最小日志与埋点。
    使用现有 KLog* / SuiCloudUserBehaviorGatheringService，记录阶段、耗时、分页数量、渲染尺寸和错误码；不要记录账本名称、流水内容或图片 URL 等敏感数据。

 最小验证建议

 - 无网络、弱网、切换网络时进入分享页：应在超时后展示默认背景的长图，不可永久 skeleton。
 - 首次加载未缓存的背景、头像和流水附件：确认渲染结果是实际图或明确占位图，不出现随机空白。
 - 1、20、21、60 条流水；分别覆盖无附件、少量附件、大量附件、超长备注。
 - 低内存设备或 Xcode Memory Gauge 下验证分页和合图；检查生成位图尺寸不会超过策略上限。
 - 标准版、专业版各走一次批量编辑 → 分享图片路径。

 结论：最优先排查“背景图双请求未完成导致根本未进入渲染”，其次是“异步网络图片仅靠固定等待导致截图时尚未加载”。分页位图尺寸和超大 section 数据遗漏是高风险边界问题，虽不一定是当前主因，但应一起修复，否则 21–60 条流水场景仍会不稳定。
